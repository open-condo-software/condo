# Address service: bulk normalization — third questions

Третий и, предположительно, последний раунд вопросов. Здесь только решения, которые остались неоднозначными после проверки существующего кода.

## Что дополнительно выяснилось из кода

- `DadataSuggestionProvider` уже получает организацию по ИНН, кэширует ответ в Redis примерно на сутки и передает `locations_boost` из `settlement_kladr_id`, `city_kladr_id` или `region_kladr_id`.
- `finance-info-client` использует отдельный Redis-кэш на 10 дней и возвращает строку `organizationAddress`, но не возвращает KLADR, координаты или структурированный город.
- Pullenti `queryBooster` отдельно запрашивает организацию в Dadata, извлекает KLADR и через Pullenti получает путь территории.
- Текущий `PullentiSearchProvider` address-service все еще использует XML-совместимость. JSON API 4.35 сейчас используется в `qualityCheck`, но еще не в основном поисковом провайдере address-service.
- Вызов обычного `AddressServiceClient` из нового endpoint того же address-service создаст лишний self-HTTP-вызов. Существующие search strategies и plugins можно переиспользовать внутри процесса.
- Существующее сохранение уже создает `Address`, heuristics и `AddressSource`, сохраняет helpers hash и не использует общую транзакцию.

   Ответ: да, finance-info-client можно не использовать 

2. Или принципиально нужно использовать именно `finance-info-client`, несмотря на отсутствие в его результате KLADR и структурированного города?

3. Если ИНН передан, но невалиден, это ошибка всего запроса HTTP 400, поскольку helpers общие для пачки? Рекомендация: да.

   Ответ: можно просто, игнорировать

## 3. Окончательный flow поиска

9. Подтверждаем flow одного элемента:

   3. Переданный `globalId` параллельно проверяется через Pullenti JSON и существующий поиск address-service.
   4. Для вариантов дома от Pullenti и наивного парсера запускается существующая цепочка address-service с Dadata provider; цепочка сама сначала проверяет `AddressSource` и heuristics.

   6. Победитель должен соответствовать настоящему `Address.id`.

   Ответ:

10. Если Pullenti и наивный парсер выделили одинаковый дом после нормализации регистра и пробелов, выполняем только один поиск. Если разные — проверяем оба. Подтверждаем?

    Ответ: ок

    Ответ: ок

15. Порог успеха 50 применяется после приведения confidence к `0..100`?

    Ответ: это была шутка - не будет порога успеха

16. Уточните ответ про конфликт ФИАС и адреса. Выбираем конкретно:

    - вариант A: вернуть дом входного ФИАС как успех и warning `CONFLICTING_ADDRESS_AND_FIAS`;
    - вариант B: вернуть `AMBIGUOUS_ADDRESS` без результата;
    - вариант C: scoring выбирает победителя, конфликт только добавляет warning.

## Уже закрыто кодом, дополнительных решений не требует

- Для адресного поиска используется существующий `DadataSearchProvider`; `finance-info-client` сам адреса не нормализует.
- Dadata provider уже применяет `locations_boost` по ИНН и сначала использует собственные кэши.
- Существующие `AddressSource`, helpers hash, heuristics и последовательное сохранение переиспользуются без изменения общего механизма.
- Общая транзакция в первой версии не добавляется.
- Снаружи возвращается `Address.id`, а внутренний `Address.key` не публикуется.
- В БД остается полный канонический адрес; поле `house` ответа формируется коротким алгоритмом из qualityCheck.
- Параллелизм будет настраиваемым, значения подбираются позже тестами.
- Авторизация, rate limit, метрики, Dadata budget counter и golden-набор не входят в первую реализацию.
