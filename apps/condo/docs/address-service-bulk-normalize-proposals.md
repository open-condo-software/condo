# Address service bulk normalization: architecture proposals

Документ содержит предложения по реализации после трех раундов согласования. Это еще не финальная техническая спецификация и не код.

## Главная идея

Обрабатывать запрос как единый batch pipeline, а не как 100 независимых вызовов нормализатора.

Типичная пачка содержит много помещений, но мало домов. Например, 100 строк начислений могут относиться к 1–5 домам. Поэтому дорогие операции нужно выполнять на уровне уникального дома, а не на уровне исходной строки.

Ожидаемая схема для 100 элементов:

- до 100 локальных разборов Pullenti;
- один запрос информации об организации по ИНН;
- 1–5 уникальных поисков домов через существующую цепочку address-service;
- 1–5 внешних запросов Dadata при отсутствии cache hit;
- 1–5 операций создания или поиска `Address`;
- сборка 100 маленьких результатов из подготовленных данных.

## Предлагаемый batch pipeline

### Этап 1. Валидация запроса

Проверить один раз:

- `items` — непустой plain object;
- количество элементов не превышает `BULK_NORMALIZE_MAX_ITEMS`, default 100, hard limit 1000;
- размер JSON body не превышает 512 KiB;
- неизвестные поля отсутствуют;
- `helpers`, `addressMeta` и их поля имеют ожидаемые типы.

Отдельные ограничения длины полей не нужны: достаточно ограничения body и количества элементов.

Невалидный `tin` лучше игнорировать, как согласовано. Он является необязательной подсказкой, а не частью адреса.

После JSON parsing значения нужно переложить во внутренние `Map` или объекты без прототипа. Исходный адрес является ключом пользовательского объекта, поэтому нельзя безопасно использовать произвольные ключи через обычные промежуточные `{}` без проверки.

### Этап 2. Подготовка контекста организации

Если передан валидный ИНН:

1. Один раз на пачку запросить организацию через существующий `DadataSuggestionProvider.getOrganization`.
2. Сохранить результат в request-scoped context.
3. Из структурированного ответа получить:
   - KLADR для `locations_boost` Dadata;
   - город или населенный пункт для дополнительного вызова Pullenti, если исходный адрес не содержит города.

Если организация не найдена или подсказка недоступна, продолжить без нее. Warning не нужен: отсутствие boost не означает проблему исходного адреса.

Важно не выполнять для каждого уникального дома отдельный Redis lookup организации. Даже кэшированный результат лучше мемоизировать на время всей пачки.

### Этап 3. Дешевый локальный разбор всех элементов

Для каждого исходного адреса запустить существующий наивный парсер и получить:

- предварительный house;
- предварительный `unitName`;
- предварительный `unitType`.

Отдельно разобрать хвост `addressMeta.globalId`, если он есть.

Результаты этого этапа не считаются истиной. Они формируют кандидатов и помогают сгруппировать пачку.

Нельзя отбрасывать ведущие нули помещения. `001` должно остаться `001`.

### Этап 4. Pullenti JSON для исходных адресов

Каждый уникальный исходный адрес обработать через Pullenti 4.35 JSON API.

Pullenti нужен для двух задач:

- точнее отделить дом от помещения, включая помещение в середине строки;
- получить независимый кандидат дома, ФИАС и коэффициент разбора.

Вызовы выполнять с ограниченным настраиваемым параллелизмом. Начальное значение лучше выбрать консервативно, например 10, а затем измерить локально.

Если Pullenti явно сообщает об отсутствии города:

1. Взять город/населенный пункт из batch context организации.
2. Повторить запрос с добавленным городом.
3. Использовать повторный результат только если его качество выше и найден подтвержденный дом.

Если подсказки организации нет, оставить первый результат.

[Изменения Pullenti 4.35](https://www.garfias.ru/Download).

### Этап 5. Проверка входных ФИАС

Все уникальные UUID из `addressMeta.globalId` дедуплицировать и проверять один раз на UUID.

Проверка выполняется параллельно с разбором адресов:

- Pullenti JSON определяет существование, актуальность, уровень и родительский дом;
- существующая search chain ищет уже сохраненный `Address` и heuristics.

Любой несуществующий, архивный или не относящийся к актуальному дому UUID дает warning `BAD_FIAS`.

После `BAD_FIAS` текстовый адрес все равно обрабатывается. Если найден дом, его `globalId` становится предложением для замены плохого ФИАС.

Таймаут, неполное покрытие региона или расхождение версий ГАР оставляют UUID непроверенным. Предлагать замену стоит при подтверждённой причине, например если UUID принадлежит помещению или архивной записи. Для UUID помещения родительский дом можно проверить как отдельного кандидата по исходному тексту, сохранив BAD_FIAS у входного UUID. Для спорных примеров подойдёт сверка с актуальной выгрузкой ФНС. ### Этап 6. Группировка кандидатов домов

Для каждого элемента будут получены как минимум два возможных house-кандидата:

- наивный парсер;
- Pullenti.

Кандидаты нужно дедуплицировать в следующем порядке:

1. По подтвержденному house/stead FIAS, если он есть.
2. Иначе по аккуратно нормализованной строке дома.

Для строковой дедупликации достаточно безопасных преобразований:

- trim;
- lowercase;
- схлопывание повторных пробелов;
- единообразные пробелы рядом с запятыми.

Не следует на этом этапе агрессивно удалять типы улиц, корпуса, литеры или заменять символы: можно ошибочно объединить разные дома.

В результате из 100 исходных строк должен получиться небольшой список уникальных house-кандидатов.

<!--
Комментарий к дедупликации. Мемоизировать одинаковый поиск по тексту и эффективным подсказкам, а оценку оставлять у каждой строки. Например, у двух помещений в одном доме могут быть разные входные UUID, поэтому BAD_FIAS или CONFLICTING_ADDRESS_AND_FIAS относится к конкретной строке. Совпадающий GUID позволяет объединить кандидатов после проверки принадлежности к одному дому. Если одинаковый текст в двух строках противоречит разным подтверждённым GUID, результаты поиска можно переиспользовать, оставив конфликт видимым.
-->

### Этап 7. Поиск уникальных домов через существующую цепочку

Каждый уникальный house-кандидат передать во внутреннюю существующую search chain с Dadata provider.

Не делать HTTP-запрос address-service в самого себя. Следует переиспользовать внутренние strategies/plugins и `createOrUpdateAddressWithSource`.

Существующая цепочка сама обеспечивает:

- поиск `AddressSource` с helpers hash;
- поиск по FIAS и heuristics;
- обращение к Dadata только при cache miss;
- создание `Address`, heuristics и `AddressSource`;
- повторное использование существующего `Address.id`.

Если результат Dadata не содержит `house_fias_id` или `stead_fias_id`, новый Address из такого результата не создается.

<!--
Комментарий к порядку записи. Сейчас `SearchByProvider.search()` и `SearchByFiasId.search()` вызывают `createOrUpdateAddressWithSource` прямо во время поиска. Если запустить цепочку для каждого кандидата, проигравший вариант может записать `AddressSource`. При повторном импорте эта привязка получит приоритет 100. Для bulkNormalize стоит переиспользовать чтение `AddressSource` и точных ФИАС-эвристик, получение и нормализацию ответа провайдера. Helper записи вызывать после выбора победителя и проверки house/stead GUID из ответа DaData.

### Этап 8. Важная особенность Pullenti persistence

Сейчас общий helper намеренно не сохраняет результат Pullenti и возвращает синтетический идентификатор. Для нового endpoint это недостаточно: успешный ответ обязан содержать настоящий `Address.id`.

Предлагаемый вариант:

- Pullenti используется как parser и независимое доказательство;
- найденный существующий Address по Pullenti FIAS допустим как результат;
- новый Address в первой версии создается только через существующую Dadata search chain;
- если Dadata недоступна, Pullenti может дать успешный результат только при наличии уже сохраненного Address;
- если сохраненного Address нет, вернуть `PROVIDER_UNAVAILABLE` или `ADDRESS_NOT_FOUND` в зависимости от причины.

Это сохраняет поведение `/bulkSearch` без изменений и не размножает новый persistence-код.

В будущем можно добавить opt-in сохранение подтвержденных Pullenti JSON результатов. Это должно быть отдельным решением, потому что текущий запрет на их сохранение оставлен в коде намеренно.

### Этап 9. Выбор победителя

Рекомендую отделить жесткие условия успеха от scoring.

Жесткие условия:

- существует настоящий `Address.id`;
- найден дом или земельный участок;
- новый результат Dadata содержит house/stead FIAS;
- нет неразрешимого равенства разных домов.

Scoring нужен для выбора между допустимыми кандидатами, но не должен сам превращать невалидный кандидат в успешный.

Утвержденные сигналы:

- точный существующий `AddressSource`: 100 и побеждает;
- точный существующий FIAS heuristic: 90;
- Dadata: 40;
- Pullenti с `coef = 100`: 40;
- входной ФИАС: 20;
- совпадение с территорией организации: 10;
- при равенстве Dadata имеет приоритет над Pullenti.

Для выбора можно использовать внутреннюю сумму. Публичный `confidence` приводится к диапазону `0..100` и является диагностикой, а не порогом успеха.

Практически лучше сохранить рядом с кандидатом не только итоговое число, но и набор причин:

```text
addressSourceHit
fiasHeuristicHit
dadataMatch
pullentiMatch
inputFiasMatch
organizationLocationMatch
```

Эти признаки не нужно отправлять клиенту, но они сильно упростят тестирование алгоритма.

<!--
Комментарий к допуску кандидатов. Наличие GUID подтверждает, что провайдер указал конкретный объект. Перед scoring стоит проверить, что этот объект соответствует явно указанным компонентам исходного адреса. Например, для «д. 12, к. 2» подсказка «д. 12» может указывать на соседний дом. То же касается строения, литеры и явно указанного населённого пункта. Сверять структурированные компоненты с учётом известных алиасов. При отсутствии корпуса во входе и нескольких подходящих домах перепроверить варианты, затем вернуть AMBIGUOUS_ADDRESS, если исходных данных для выбора по-прежнему мало. `coef = 100` использовать как качество разбора. [Поля дома и корпуса в API DaData](https://dadata.ru/api/suggest/address/).

Для scoring также важно происхождение сигнала. Вызов DaData по входному UUID и точный hit ФИАС-эвристики по тому же UUID подтверждают существование и привязку GUID. Если сохранённый AddressSource победил по согласованному правилу, а провайдеры согласны между собой и указывают на другой дом, сохранить причину расхождения во внутренней диагностике для проверки устаревших привязок.
-->

### Этап 10. Конфликт ФИАС и адреса

При конфликте вернуть выбранный scoring-алгоритмом результат и warning `CONFLICTING_ADDRESS_AND_FIAS`.

Если входной ФИАС плохой, но текстовый адрес успешно распознан:

- результат содержит корректный `globalId` найденного дома;
- warnings содержит `BAD_FIAS`;
- потребитель сможет предложить заменить входной ФИАС.

Если два допустимых кандидата остаются равнозначными после всех tie-break правил, вернуть `AMBIGUOUS_ADDRESS`.

### Этап 11. Помещение

Окончательный приоритет:

```text
unitName:
addressMeta.unitName > globalId tail > Pullenti > naive parser

unitType:
valid addressMeta.unitType > Pullenti > globalId tail > naive parser
```

Невалидный `addressMeta.unitType` молча не участвует в выборе.

Пока нет надежного признака частного дома:

- отсутствие apartment в Pullenti не означает квартиру №1;
- если помещение не найдено, возвращается `unitName: null`, `unitType: null`;
- правило `flat / 1` добавляется позже на основании реальных JSON-примеров Pullenti.

Warning `UNIT_NOT_FOUND` лучше добавлять не для каждого адреса без помещения, а только если вход явно похож на содержащий помещение:

- передан `addressMeta.unitName`;
- у `globalId` есть хвост;
- в адресе найден маркер квартиры/офиса/помещения;
- Pullenti вернул apartment, который не удалось преобразовать.

Для обычного адреса дома отсутствие помещения не является ошибкой или предупреждением.

<!--
Комментарий к помещению. Хранить разобранные кандидатами `unitName` и `unitType` вместе с их источником. Согласованный приоритет может дать «офис 001», если хвост `globalId` содержит «кв 001», а Pullenti разобрал «оф 7». Предлагаю подставлять тип из другого источника только при совпадении номера и брать номер как строку. Помещение из структурированного результата провайдера использовать, когда его дом совпал с победителем. Явные данные исходной строки и addressMeta можно сверять отдельно.
-->

### Этап 12. Сохранение по уникальным домам

Создание и поиск Address должны происходить один раз на уникальный дом, а не один раз на элемент.

После выбора победителей:

1. Сгруппировать элементы по победившему дому.
2. Для каждого дома получить один настоящий `Address.id`.
3. Раздать этот id всем помещениям данного дома.

`AddressSource` содержит только варианты адреса дома. Полный исходный адрес с квартирой туда не записывается, чтобы не создавать тысячи sources для одного здания.

<!--
Комментарий к записи победителя. `createOrUpdateAddressWithSource` умеет подобрать существующий Address по координатам или fallback-ключу. Общие координаты соседних корпусов могут склеить разные GUID. Для bulkNormalize стоит проверить идентичность дома до записи эвристик и алиасов. При параллельных запросах повторно читать запись после конфликта уникальности. Существующая привязка того же алиаса к другому дому требует разрешения конфликта, поскольку текущий upsert может её переписать. В ответе `id` и `globalId` должны ссылаться на один объект.
-->

### Этап 13. Сборка ответа

Ответ индексируется исходным адресом:

```json
{
    "items": {
        "исходный адрес": {
            "result": {
                "id": "Address.id",
                "house": "короткий адрес дома",
                "globalId": "uuid или null",
                "unitName": "001 или null",
                "unitType": "flat или null",
                "confidence": 100
            },
            "warnings": [],
            "error": null
        }
    }
}
```

Ошибка элемента:

```json
{
    "result": null,
    "warnings": ["BAD_FIAS"],
    "error": {
        "code": "ADDRESS_NOT_FOUND",
        "stage": "resolve-house",
        "message": "No house candidate was resolved"
    }
}
```

`message` технический, без локализации, stack trace и сырых ответов провайдеров.

## Warning codes первой версии

- `BAD_FIAS`;
- `CONFLICTING_ADDRESS_AND_FIAS`;
- `UNIT_NOT_FOUND` — только если помещение ожидалось;
- `DADATA_UNAVAILABLE`;
- `PULLENTI_UNAVAILABLE`.

Подсказка организации является необязательной, поэтому `ORGANIZATION_HINT_UNAVAILABLE` можно не возвращать: иначе одна проблема организации создаст одинаковый warning у всех 100 элементов и увеличит ответ.

## Error codes первой версии

- `INVALID_INPUT`;
- `ADDRESS_NOT_FOUND`;
- `AMBIGUOUS_ADDRESS`;
- `PROVIDER_UNAVAILABLE`.

Комментарий к статусам. `DadataSuggestionProvider.get()` возвращает `[]` и при пустом ответе, и после ошибки запроса. Для нового пути нужен внутренний результат, различающий пустую выдачу и сбой. Если без упавшего провайдера невозможно завершить поиск, возвращать PROVIDER_UNAVAILABLE. Если другой источник дал допустимого победителя, достаточно success с предупреждением о сбое. ## Как еще сократить число запросов

### Request-scoped memoization

В рамках одного HTTP-запроса кэшировать promises по ключам:

- `organization:<tin>`;
- `pullenti-address:<raw-address>`;
- `pullenti-fias:<uuid>`;
- `house-search:<normalized-house>|<helpers-hash>`.

Кэшировать именно Promise удобно: два параллельных элемента не успеют одновременно запустить одинаковый внешний запрос.

### Ограниченная параллельность вместо chunk loops

Не запускать все 100 запросов одновременно и не обрабатывать строго последовательно. Использовать worker pool с отдельными лимитами:

- Pullenti concurrency;
- address-service/Dadata concurrency;
- FIAS lookup concurrency.

Лимиты должны быть конфигурируемыми.

### Двухпроходная Dadata

В обычном случае запрашивать один результат, как сейчас.

Только если первый результат конфликтует с Pullenti или входным ФИАС, можно вторым проходом запросить несколько Dadata suggestions. Это почти не увеличит обычную нагрузку, но поможет разбирать неоднозначные адреса.

Такое улучшение лучше оставить после первых тестов: существующий `DadataSearchProvider` сейчас ориентирован на первый результат.

### Долгоживущий кэш Pullenti parsing

Pullenti локальный, поэтому в первой версии достаточно request memoization.

Если измерения покажут, что повторный разбор становится узким местом, можно добавить Redis cache по полному исходному адресу. В ключ внутреннего кэша обязательно должна входить версия формата Pullenti/индекса, чтобы после обновления 4.35 не использовать старые результаты.

## Что я бы не делал в первой версии

- Не создавал отдельную очередь и асинхронную job-модель для пачек по 100.
- Не сохранял помещения как отдельные AddressSource.
- Не добавлял агрессивную нечеткую дедупликацию строк домов.
- Не строил сложную ML-модель confidence.
- Не менял `/bulkSearch` и общий Pullenti provider.
- Не добавлял новый persistence-механизм рядом с существующим.
- Не пытался определить частный дом без реальных Pullenti JSON-примеров.
- Не добавлял подробную диагностику провайдеров в публичный ответ.

## Предлагаемый порядок реализации после утверждения спеки

1. Контракт, валидация и пустой pipeline с fake providers.
2. Batch parser и группировка уникальных домов.
3. Pullenti 4.35 JSON adapter.
4. Проверка и дедупликация ФИАС.
5. Переиспользование внутренней search chain с Dadata provider.
6. Scoring и разрешение конфликтов.
7. Unit resolution.
8. Короткий house и формирование ответа.
9. Метод `bulkNormalize` в `address-service-client` и fake client.
10. Unit/integration tests и затем реальные golden-примеры.
