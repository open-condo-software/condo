# Bulk normalization API for address-service

Статус: **Draft for review by address-service maintainer**  
Целевой endpoint: `POST /bulkNormalize`  
Основная реализация: `apps/address-service`  
Клиент: `packages/clients/address-service-client`

## 1. Контекст

Несколько приложений Condo независимо решают одну задачу: выделяют дом и помещение из строки, проверяют ФИАС, обращаются к Pullenti и Dadata, ищут `Address` и формируют собственные ошибки.

Планируется единый синхронный endpoint address-service для массовой нормализации адресов. Первые потребители будут отправлять адреса пачками; типичная пачка содержит много помещений, но небольшое количество уникальных домов.

Первая версия endpoint реализуется и тестируется отдельно. Существующие потребители пока не переключаются.

## 2. Цели

Endpoint должен:

1. Обработать до 100 адресов за запрос по умолчанию с возможностью увеличить лимит до 1000.
2. Выделить дом и помещение.
3. Проверить переданный ФИАС и предложить актуальный ФИАС дома при подтвержденной ошибке.
4. Использовать Pullenti 4.35 JSON API, существующую базу address-service и Dadata.
5. Возвращать только данные, необходимые вызывающему сервису.
6. Дедуплицировать операции по организации, исходному адресу, ФИАС и дому внутри пачки.
7. Создавать или связывать только победивший дом, не сохраняя проигравшие варианты.
8. Возвращать настоящий `Address.id` для каждого успешного результата.
9. Обрабатывать ошибки отдельных элементов независимо.

## 3. Не входит в первую версию

- Изменение или удаление `/bulkSearch`.
- Переключение существующих потребителей.
- Изменение `PropertyResolver`, qualityCheck и cottage village logic.
- Асинхронные jobs и очереди.
- Новая модель хранения помещений.
- ML-модель или сложная статистическая модель confidence.
- Платная стандартизация Dadata.
- Постоянный Redis-кэш Pullenti parsing.
- Общая транзакция на всю пачку.
- Авторизация, отдельный rate limit, счетчик бюджета Dadata и новые продуктовые метрики.
- Автоматическое определение частного дома до появления размеченных Pullenti JSON-примеров.

## 4. Совместимость

- `/bulkNormalize` является новым endpoint.
- `/bulkSearch` и его поведение не меняются.
- Текущий XML `PullentiSearchProvider` не переписывается в рамках задачи.
- Для bulk normalization создается отдельный адаптер Pullenti 4.35 JSON.
- В `AddressServiceClient` и `FakeAddressServiceClient` добавляется метод `bulkNormalize`.

## 5. География

Первая версия поддерживает только адреса РФ.

Допустимыми leaf-объектами считаются:

- дом с `house_fias_id`;
- земельный участок с `stead_fias_id`.

Во внешнем ответе оба варианта представлены как дом с единым полем `globalId`.

## 6. HTTP contract

### 6.1 Request

```http
POST /bulkNormalize
Content-Type: application/json
```

```json
{
    "items": {
        "РОССИЯ, Краснодарский край, Новороссийск, ул Черняховского, д 19, кв.001": {
            "addressMeta": {
                "globalId": "a06eb7a2-18e4-4d0d-8193-6c1cddcc1274,кв 001",
                "unitName": null,
                "unitType": null
            }
        },
        "г Москва, ул Хабаровская, д 5": {
            "addressMeta": {}
        }
    },
    "helpers": {
        "tin": "7707083893"
    }
}
```

### 6.2 Request schema

```text
BulkNormalizeRequest
  items: Record<address, BulkNormalizeItem>     required
  helpers?:
    tin?: string

BulkNormalizeItem
  addressMeta?:
    globalId?: string | null
    unitName?: string | null
    unitType?: UnitType | string | null
```

Адрес является ключом `items`. Поэтому:

- поле `address` внутри элемента отсутствует;
- одинаковая строка не может дважды присутствовать с разными metadata;
- ответ индексируется той же исходной строкой;
- порядок ключей не является частью контракта.

### 6.3 UUID вместо адреса

Если ключ `items` является UUID и `addressMeta.globalId` не передан:

- ключ трактуется как `globalId`;
- текстовый адрес считается отсутствующим;
- нормализация выполняется по ФИАС.

Одновременная передача UUID в ключе и другого `addressMeta.globalId` является `INVALID_INPUT` для элемента.

### 6.4 UnitType

Поддерживаются значения из `apps/condo/domains/property/constants/common.js`:

- `flat`;
- `parking`;
- `apartment`;
- `commercial`;
- `warehouse`.

Русские значения в `addressMeta.unitType` не поддерживаются. Неизвестное значение молча исключается из расчетов.

### 6.5 Limits

- JSON body: не более 512 KiB.
- Количество items: от 1 до `BULK_NORMALIZE_MAX_ITEMS`.
- `BULK_NORMALIZE_MAX_ITEMS`: default 100.
- Абсолютный hard limit: 1000.
- Отдельные лимиты длины строк не вводятся в первой версии.

### 6.6 Validation

Весь запрос получает HTTP 400 при:

- malformed JSON;
- отсутствии или неправильном типе `items`;
- пустом `items`;
- превышении размера body или числа элементов;
- неизвестных полях верхнего уровня или вложенных DTO.

Семантическая ошибка конкретного элемента возвращается внутри элемента как `INVALID_INPUT`; остальные элементы продолжают обрабатываться.

`helpers.tin` необязателен. Невалидный, не найденный или временно недоступный ИНН игнорируется: нормализация продолжается без location boost.

### 6.7 Successful response

```json
{
    "items": {
        "РОССИЯ, Краснодарский край, Новороссийск, ул Черняховского, д 19, кв.001": {
            "result": {
                "id": "f231be1b-6920-4c62-904f-6de216a3975b",
                "house": "г Новороссийск, ул Черняховского, д 19",
                "globalId": "8d84d693-4716-4bc6-9c44-01e1919a25a5",
                "unitName": "001",
                "unitType": "flat",
                "confidence": 100
            },
            "warnings": [
                "BAD_FIAS"
            ],
            "error": null
        }
    }
}
```

Поля результата стабильны и присутствуют всегда. Отсутствующие значения возвращаются как `null`.

`id` — это `Address.id`. Внутреннее поле `Address.key` наружу не возвращается.

`globalId` всегда содержит lowercase house/stead FIAS либо `null` для ранее существующего Address без ФИАС.

`house` — короткий адрес для межсервисного обмена. В `Address.address` сохраняется полный канонический адрес.

### 6.8 Element error

```json
{
    "result": null,
    "warnings": [
        "BAD_FIAS"
    ],
    "error": {
        "code": "ADDRESS_NOT_FOUND",
        "stage": "resolve-house",
        "message": "No house candidate was resolved"
    }
}
```

`message` является коротким техническим сообщением:

- без локализации;
- без stack trace;
- без полного ответа внешнего провайдера;
- без секретов и конфигурации.

Допустимые `stage` первой версии:

- `validate`;
- `parse`;
- `pullenti`;
- `fias`;
- `resolve-house`;
- `persist`.

### 6.9 HTTP statuses

- `200` — форма запроса корректна; отдельные элементы могут содержать ошибки.
- `400` — невалидная форма всего запроса.
- `5xx` — endpoint не смог сформировать корректный ответ для пачки из-за общей внутренней ошибки.

Верхнеуровневые `processed`, `succeeded`, `failed` и `durationMs` не возвращаются.

## 7. Warning codes

### `BAD_FIAS`

Входной UUID подтвержден как требующий замены:

- объект не существует;
- объект архивный;
- объект относится к квартире или помещению;
- объект относится к улице, городу или другому уровню вместо дома/участка;
- UUID относится к неактуальному дому.

Таймаут или ошибка провайдера сами по себе не являются `BAD_FIAS`.

### `CONFLICTING_ADDRESS_AND_FIAS`

Подтвержденный входной ФИАС и текстовый адрес указывают на разные дома. Endpoint возвращает выбранный scoring-алгоритмом результат и warning.

### `UNIT_NOT_FOUND`

Помещение ожидалось, но определить его не удалось. Warning ставится только если помещение явно ожидалось:

- передан `addressMeta.unitName`;
- `globalId` содержит хвост после UUID;
- в исходном адресе найден маркер помещения;
- Pullenti вернул apartment, который не удалось преобразовать.

Обычный адрес дома без помещения не получает этот warning.

### `DADATA_UNAVAILABLE`

Dadata завершилась ошибкой, но другой источник позволил вернуть успешный результат.

### `PULLENTI_UNAVAILABLE`

Pullenti завершилась ошибкой, но другой источник позволил вернуть успешный результат.

Отсутствие `globalId` не является warning. Ошибка или отсутствие organization hint также не возвращается в каждом элементе.

## 8. Error codes

### `INVALID_INPUT`

Семантически некорректен конкретный элемент.

### `ADDRESS_NOT_FOUND`

Все необходимые источники завершили работу, но допустимый дом не найден.

### `AMBIGUOUS_ADDRESS`

Найдены разные допустимые дома, а утвержденные правила и tie-break не позволяют выбрать один.

### `PROVIDER_UNAVAILABLE`

Нужный для завершения поиска провайдер недоступен, и оставшихся данных недостаточно для результата.

Пустой результат провайдера должен отличаться от сетевой или внутренней ошибки.

## 9. Основные принципы pipeline

1. Обработка выполняется на уровне всей пачки.
2. Вычисления и внешние вызовы дедуплицируются.
3. Scoring и warnings сохраняются отдельно для каждой исходной строки.
4. Поиск кандидатов выполняется без записи.
5. В БД сохраняется только победивший дом.
6. Помещение не участвует в `AddressSource`.

## 10. Batch pipeline

### 10.1 Request context

В начале запроса создается request-scoped context с memoized promises:

```text
organization:<tin>
pullenti-address:<raw-address>
pullenti-object-params:<pullenti-object-id>
pullenti-fias:<uuid>
address-by-fias:<uuid>
house-search:<normalized-house>|<effective-hint-hash>
```

Кэширование Promise предотвращает одновременный запуск одинаковых запросов.

### 10.2 Organization hint

Если передан валидный ИНН:

1. Один раз получить организацию через существующий `DadataSuggestionProvider.getOrganization`.
2. Извлечь KLADR location boost.
3. Извлечь структурированный город или населенный пункт.
4. Передавать подготовленный hint в каждый Dadata-вызов явно.

Для нового пути провайдер должен принимать подготовленный organization hint. Иначе текущий `get()` продолжит самостоятельно выполнять `getOrganization(tin)` для каждого уникального дома.

Существующее поведение `/bulkSearch` сохраняется: если подготовленный hint не передан, провайдер продолжает получать организацию самостоятельно.

Город организации добавляется к Pullenti-запросу только когда Pullenti указал на отсутствие населенного пункта во входном адресе.

Один organization hint, использованный Pullenti и Dadata, считается одним географическим сигналом, а не двумя независимыми подтверждениями.

### 10.3 Naive parsing

Для каждого исходного адреса существующий `AddressFromStringParser` получает:

- предварительный house;
- предварительный `unitName`;
- предварительный `unitType`.

Отдельно разбирается хвост `addressMeta.globalId` после первой запятой. Весь остаток считается описанием одного помещения.

Наивный результат является кандидатом, а не окончательным ответом.

### 10.4 Pullenti JSON parsing

Каждый уникальный исходный адрес обрабатывается через Pullenti 4.35 JSON API:

- `processAddressJson`;
- `searchByGuidJson`;
- `getGarObjectParams`.

Pullenti используется для:

- выделения дома и помещения;
- распознавания помещения в нетипичном месте строки;
- формирования независимого кандидата дома;
- оценки качества разбора;
- проверки уровня и актуальности ФИАС.

Для массовой обработки вызовы ограничиваются worker pool. Исходные адреса допустимо предварительно сортировать лексикографически, если серверный JSON API предоставляет и корректно изолирует режим ускорения Pullenti.

#### Pullenti 4.35 object identity

В Pullenti 4.35 объект использует числовые ObjectIds, а ФИАС GUID запрашивается отдельно как параметр объекта. Объект может иметь несколько ObjectIds; виртуальный объект может не иметь ни одного.

Требования:

- дедуплицировать `getGarObjectParams` по Pullenti object id на всю пачку;
- выбрать актуальный GUID дома/участка при нескольких значениях;
- не считать виртуальный объект подтвержденным домом без house/stead GUID;
- покрыть выбор GUID интеграционными тестами на реальном Pullenti 4.35.

### 10.5 FIAS validation

Уникальные UUID проверяются один раз и параллельно с разбором текста.

Внутреннее состояние проверки:

```text
CONFIRMED_HOUSE
CONFIRMED_BAD
UNVERIFIED
```

- `CONFIRMED_HOUSE` — найден актуальный дом/участок.
- `CONFIRMED_BAD` — подтверждено, что UUID отсутствует, архивный или относится не к актуальному дому/участку.
- `UNVERIFIED` — проверка не завершилась надежно из-за таймаута, ошибки или неполных данных.

Только `CONFIRMED_BAD` формирует `BAD_FIAS`.

Для ФИАС помещения родительский дом становится отдельным кандидатом, но входной UUID остается `BAD_FIAS`.

### 10.6 House candidates

Для элемента формируются кандидаты из:

- точного `AddressSource`;
- точной FIAS heuristic;
- входного ФИАС;
- Pullenti;
- Dadata;
- наивно выделенной строки дома.

House-кандидаты дедуплицируются:

1. По подтвержденному house/stead GUID.
2. Иначе по безопасно нормализованной строке.

Безопасная нормализация строки:

- trim;
- lowercase;
- схлопывание повторных пробелов;
- единообразные пробелы рядом с запятыми.

Корпус, строение, литера и типы адресных объектов не удаляются.

Одинаковый внешний поиск может переиспользоваться разными элементами, но их входной ФИАС, scoring и warnings остаются независимыми.

### 10.7 Read-only resolution

Нельзя запускать существующую mutating search chain для каждого кандидата: `SearchByProvider` и `SearchByFiasId` сохраняют результат во время поиска.

Для bulk normalization нужны отдельные внутренние стадии:

1. Прочитать `AddressSource` и точные heuristics.
2. Получить и нормализовать ответы провайдеров без записи.
3. Проверить допустимость кандидатов.
4. Выполнить scoring.
5. Выбрать победителя.
6. Только затем вызвать общий persistence helper для победителя.

Нужно переиспользовать существующие provider normalizers, database readers и `createOrUpdateAddressWithSource`, но не существующую end-to-end strategy с побочными эффектами.

### 10.8 Dadata resolution

Dadata вызывается только для уникальных house-кандидатов и только после cache miss.

Новый Address из ответа Dadata допускается только при наличии:

- `house_fias_id`; или
- `stead_fias_id`.

Первый suggestion не считается достаточным доказательством соответствия исходной строке. До scoring проверяются явно указанные компоненты:

- населенный пункт;
- номер дома;
- корпус;
- строение;
- литера.

Если первый результат:

- остановился на уровне улицы;
- потерял явно указанный компонент;
- конфликтует с Pullenti или входным ФИАС;
- допускает несколько домов;

выполняется один дополнительный запрос с `count: 3..5`. Ответ переиспользуется всей пачкой для данного house-кандидата.

Если Pullenti дал точный GUID, допустима проверка через Dadata `findById/address` с последующей сверкой house/stead GUID и компонентов.

### 10.9 Component validation

Наличие GUID доказывает существование объекта, но не совпадение с исходным адресом.

Перед scoring кандидат проверяется против явно распознанных компонентов исходной строки. Несовпадение дома, корпуса, строения, литеры или явно указанного населенного пункта исключает кандидата либо делает результат неоднозначным.

В первой версии не требуется универсальный fuzzy matcher. Достаточно:

- структурированных полей Pullenti и Dadata;
- нормализации регистра, пробелов и распространенных сокращений типов;
- точного сравнения значимых номерных компонентов.

<!--
Комментарий ревью. В проверках §10.8–10.9 явно добавить улицу или иной адресный объект, которому принадлежит дом, и явно указанный регион. Иначе «г Тула, ул Ленина, д. 12» может совпасть с «г Тула, ул Советская, д. 12» по всему списку. ### 10.10 Provider status

Внутренний provider result должен различать:

```text
SUCCESS
NOT_FOUND
FAILED
```

Текущий `DadataSuggestionProvider.get()` возвращает пустой массив и при пустой выдаче, и при ошибке. Для нового read-only пути нужен status-aware wrapper или новый внутренний метод. Поведение существующего `get()` для `/bulkSearch` не меняется.

## 11. Candidate scoring

### 11.1 Hard admission rules

До scoring кандидат должен пройти обязательные проверки:

- относится к дому или земельному участку;
- не противоречит явно указанным компонентам адреса;
- для нового Dadata Address содержит house/stead GUID;
- может быть связан с настоящим `Address.id` после выбора.

Scoring не может превратить недопустимый кандидат в успешный.

### 11.2 Signals

| Сигнал | Вес | Примечание |
|---|---:|---|
| Точный существующий `AddressSource` | 100 | Имеет абсолютный приоритет в первой версии |
| Точная существующая FIAS heuristic | 90 | Подтверждает известный Address |
| Dadata совпала с кандидатом | 40 | После component validation |
| Pullenti совпала с кандидатом | 40 | Только при `coef = 100` |
| Валидный входной ФИАС совпал | 20 | Не является подтверждением текста сам по себе |
| Территория организации совпала | 10 | Добавляется один раз |

При равенстве Dadata имеет приоритет над Pullenti.

Если после tie-break остаются разные равнозначные дома, возвращается `AMBIGUOUS_ADDRESS`.

Точный `AddressSource` побеждает даже при расхождении провайдеров, как принято для первой версии. Расхождение сохраняется во внутренней диагностике для поиска устаревших привязок.

<!--
Комментарий ревью. Зафиксировать порядок hard admission, абсолютного приоритета cache hit и сравнения ФИАС с текстом. Например, входной актуальный GUID и точный AddressSource ведут на д. 12, а исходная строка явно содержит «д. 12, к. 2». Предлагаю применять приоритет AddressSource среди допустимых кандидатов и вычислять CONFLICTING_ADDRESS_AND_FIAS по исходным данным до фильтрации ФИАС-кандидата. Уточнить, что DaData-запрос по входному UUID подтверждает привязку имеющегося UUID, а вес за совпадение с текстом начисляется только по отдельной проверке исходного текста.
-->

### 11.3 Confidence

`confidence` является временной диагностикой, а не порогом успеха.

Значение вычисляется из внутреннего score и ограничивается диапазоном `0..100`. Порог успеха отсутствует: успех определяется hard admission rules и возможностью получить настоящий `Address.id`.

Внутри кандидата сохраняются причины score, но наружу не возвращаются:

```text
addressSourceHit
fiasHeuristicHit
dadataMatch
pullentiMatch
inputFiasMatch
organizationLocationMatch
```

## 12. Conflict rules

### 12.1 AddressSource conflict

Точный существующий `AddressSource` побеждает. Расхождение с согласованными Pullenti/Dadata фиксируется во внутренней диагностике, но не меняет результат первой версии.

### 12.2 Input FIAS vs textual address

Выбирается победитель scoring-алгоритма. В ответ добавляется `CONFLICTING_ADDRESS_AND_FIAS`.

### 12.3 Duplicate FIAS heuristics

Если один house/stead GUID связан с несколькими активными Address и невозможно определить один, возвращается `AMBIGUOUS_ADDRESS`.

### 12.4 AddressSource alias conflict during persistence

Существующий alias нельзя автоматически перепривязать к другому дому. Такая ситуация возвращает `AMBIGUOUS_ADDRESS` либо использует уже привязанный Address согласно правилу точного `AddressSource`.

## 13. Unit resolution

### 13.1 Candidate representation

Каждый источник возвращает unit candidate как связанную структуру:

```text
unitName
unitType
source
houseCandidateId
```

Unit от провайдера используется только если дом провайдера совпал с победившим домом.

### 13.2 Priorities

```text
unitName:
addressMeta.unitName > globalId tail > Pullenti > naive parser

unitType:
valid addressMeta.unitType > Pullenti > globalId tail > naive parser
```

Правила объединения:

1. Явный `addressMeta.unitName` и валидный `addressMeta.unitType` имеют независимый высший приоритет.
2. Если явным является только одно поле, второе можно получить из другого источника.
3. Неявные `unitName` и `unitType` из разных источников объединяются только когда их нормализованные unitName совпадают.
4. Иначе используется пара из источника выбранного `unitName`.

Это предотвращает комбинации вроде `офис 001`, если один источник распознал `кв 001`, а другой `оф 7`.

<!--
Комментарий ревью. Пункт 2 оставляет тот же риск при явном `addressMeta.unitName: "001"` и Pullenti «оф. 7». Применить проверку совпадения номера и к этому случаю. Также указать, что делать с хвостом globalId при подтверждённом конфликте домов. Например, если UUID ведёт на дом A, а победил дом B, предлагаю брать хвост только при независимом подтверждении номера у дома B. Иначе использовать явные поля или помещение из исходной строки по правилам выше.
-->

### 13.3 Unit format

- `unitName` остается строкой.
- Ведущие нули сохраняются.
- Все после первой запятой в `globalId` считается единым unit description.
- `кв.1, ком.1, 2, 3, 4` может дать один `unitName`: `1, ком.1, 2, 3, 4`.
- Несколько перечисленных квартир считаются одним unit.
- Этаж, подъезд и секция при наличии остаются частью unitName.
- `комната` отображается в `flat`.

### 13.4 Missing unit

Пока нет надежного признака частного дома:

- отсутствие apartment не означает квартиру №1;
- возвращается `unitName: null`, `unitType: null`;
- `UNIT_NOT_FOUND` ставится только когда помещение явно ожидалось.

## 14. Persistence

### 14.1 Commit only winner

После scoring элементы группируются по победившему дому. Для каждого уникального победителя persistence выполняется один раз.

Проигравшие кандидаты не создают:

- `Address`;
- `AddressSource`;
- heuristics.

### 14.2 Existing Address without FIAS

Ранее сохраненный Address без ФИАС может быть успешным результатом.

Новый Address без house/stead FIAS в первой версии не создается.

### 14.3 Pullenti persistence

Pullenti используется как parser и источник доказательства.

Pullenti может дать успешный результат без Dadata, если соответствующий Address уже существует по `AddressSource` или heuristic.

Если Address не существует, новый объект в первой версии создается через подтвержденный Dadata result. Это не меняет текущий запрет общего helper на сохранение Pullenti addresses.

### 14.4 AddressSource

- В `AddressSource` сохраняются только варианты адреса дома.
- Полный исходный адрес с помещением не сохраняется как source.
- Сохраняется существующее поведение helpers hash.
- Канонический `Address.address` остается source candidate согласно существующему helper.

<!--
Комментарий ревью. У победы дома и сохранения короткого алиаса разные условия. Например, строки «ул Ленина, д. 5, кв. 1» и «ул Ленина, д. 5, кв. 2» могут корректно разрешиться в разных городах по своим UUID. Общая строка дома с одинаковым helpers hash при этом неоднозначна. Предлагаю сохранять алиас только когда сама строка с этими helpers определяет дом однозначно, без metadata конкретной строки. Проверять ключи алиасов по всей пачке до записи. Также отфильтровать помещение из канонической строки до использования её как алиаса. Нормализатор DaData сейчас копирует `value` и поля квартиры целиком.
-->

### 14.5 Identity checks

Перед записью проверяется, что:

- house/stead GUID победителя соответствует возвращаемому `globalId`;
- существующий Address с точной FIAS heuristic не противоречит победителю;
- координатная или fallback heuristic не склеивает разные подтвержденные GUID;
- `Address.id` и `globalId` ответа относятся к одному объекту.

### 14.6 Concurrency

При конфликте уникальности из-за параллельного создания одного дома:

1. Повторно прочитать Address/heuristics.
2. Проверить identity.
3. Вернуть существующий `Address.id`, если это тот же дом.
4. Иначе вернуть `AMBIGUOUS_ADDRESS` или internal persistence error.

Общая транзакция первой версии не требуется.

## 15. Short house formatting

Логика соответствует текущему qualityCheck, но реализуется внутри address-service, без импорта кода другого приложения.

- Удаляется страна.
- Для города удаляются region area и district.
- Для region city удаляется district.
- Для locality сохраняются необходимые region/area/settlement/locality части.
- Apartment/unit исключается.
- Дом, корпус, строение и литера сохраняются.

## 16. Performance

### 16.1 Deduplication levels

Внутри одного запроса дедуплицируются:

- исходные строки;
- organization lookup;
- Pullenti object params;
- входные UUID;
- house candidates;
- Dadata suggestions;
- persistence победившего дома.

### 16.2 Concurrency

Используются отдельные настраиваемые worker pools:

- Pullenti address parsing;
- Pullenti/FIAS object lookup;
- read-only house resolution/Dadata;
- persistence.

Предлагаемые config keys:

```text
BULK_NORMALIZE_PULLENTI_CONCURRENCY
BULK_NORMALIZE_FIAS_CONCURRENCY
BULK_NORMALIZE_PROVIDER_CONCURRENCY
BULK_NORMALIZE_PERSIST_CONCURRENCY
```

Начальные значения выбираются консервативно и уточняются после benchmark.

### 16.3 Sorting for Pullenti

Pullenti 4.35 документирует ускорение массовой обработки при лексикографической сортировке адресов и включенном accelerate mode.

Перед использованием нужно проверить, доступна ли эта опция через развернутый OpenAPI-сервер и безопасна ли она при параллельных запросах. Если нет — сортировка не должна менять семантику первой версии.

### 16.4 Timeout behavior

- Endpoint синхронный.
- Частичный ответ из-за общего timeout не формируется.
- Ошибка отдельного провайдера может быть обработана fallback-логикой элемента.
- Общая невозможность сформировать пачку возвращает 5xx.

SLA 1–2 секунды является гипотезой, а не требованием первой версии.

## 23. Варианты улучшений по результатам исследования

### 23.1 Сохранность идентификатора помещения

Pullenti может менять числовое представление, выбирать первое помещение из списка и переставлять уровни квартиры, комнаты или кладовой. Успех определения дома при этом сохраняется.

В исправленном прогоне осталось 99 успешных ответов с отличием номера от явного разбора исходного текста. Среди них встречаются `нп.XV → 15`, `нп.II → 2/1` и изменение длинного списка помещений.

Предлагается хранить исходное описание помещения и происхождение выбранных полей, а при выборе учитывать сохранность дробей, списков, ведущих нулей и вложенных уточнений. Для римских обозначений и нескольких связанных помещений полезно определить допустимые преобразования на размеченных примерах.

Изменение приоритета источников в §13.2 следует оценить на отдельной выборке. Совпадение первой числовой группы само по себе может оказаться недостаточным доказательством идентичности сложного помещения.

### 23.2 Географический контекст импорта

Населенный пункт часто отсутствует во входе. Юридический адрес по ИНН помогает поиску, но организация может обслуживать дома в нескольких населенных пунктах.

Pullenti с добавленным городом организации и Dadata с location boost используют общую подсказку. Ее происхождение нужно учитывать при оценке согласия провайдеров.

Для ИНН `6417001343` адрес `ул.Войтенко, д.5` исходная версия связывала с Сириусом. После поддержки `им.` и `имени` появился кандидат `г Красный Кут, ул им Войтенко, д 5`, совпадающий с территорией организации. GUID изменился у 22 помещений. Правильную привязку нужно подтвердить данными клиента.

Возможное расширение контракта состоит в явной передаче территории обслуживания, если она известна потребителю. Внутренняя диагностика должна сохранять основания выбора города и использование organization hint. Расширение helpers остается предложением для следующей версии.

### 23.3 Scoring с учетом происхождения доказательств

Наблюдаемые 506 переходов из ambiguity в успех при повторе требуют проверки влияния AddressSource и существующих FIAS heuristics.

Предлагается отдельно оценивать подтверждение совпадения исходной строки с домом и техническое нахождение сохраненного `Address.id`. Один вариант состоит в начислении 90 баллов точной ФИАС-эвристики при совпадении с явно переданным UUID. Нахождение существующего Address для GUID, предложенного провайдером по тексту, тогда используется для persistence.

Это изменение scoring-политики из §11.2 остается гипотезой. Его следует сравнить на размеченных примерах, при перестановке организаций и на пустой и прогретой БД.

### 23.4 Сравнение структурированных компонентов

Сейчас часть структурированного ответа провайдера форматируется в строку, которая повторно разбирается регулярными выражениями для component validation. При этом могут теряться типы и родительские связи адресных объектов.

Предлагается передавать компоненты напрямую из адаптеров, сохраняя номера дома, корпуса, строения, литеры и иерархию территории вместе с источником данных. Короткий `house` можно форматировать при сборке ответа.

Общие преобразования сокращений и порядковых названий должны сопровождаться отрицательными примерами. Следующее расширение словаря стоит выбирать по повторяемости паттерна у разных организаций.

### 23.5 Диагностика отсутствующего GUID и обозначений поставщика

Dadata иногда возвращает адрес до дома с заполненным номером и пустым `house_fias_id`. Такое наблюдалось для `ул Михаила Дорохова, д 156а` в Уфе. По текущему контракту новый Address требует house/stead GUID, поэтому визуально подходящая подсказка может остаться неразрешенной.

Отдельного исследования требуют обозначения `д.95_Х`, `парк.19/1`, `коттедж 1` и неизвестные маркеры помещений. Их значение может зависеть от поставщика данных.

Предлагается сохранять внутреннюю причину отказа, различающую отсутствие допустимого кандидата в реестре, неподдержанный разбор и неоднозначность нескольких домов. Эти причины помогут выбирать общие улучшения и определять случаи, где нужен контекст клиента.

### 23.6 Проверка UUID-ветки на фактическом Pullenti API

На локальном сервере 4.35 проверены Swagger и реальные ответы. `GarItem` содержит `spelling`, `id`, `parentIds`, `objectIds`, `actual` и `gps`.

В Swagger у `GarItem` отсутствуют поля `level` и `path`, которые сейчас ожидаются в `PullentiJsonProvider.findByGuid`. Перед использованием проверки входных UUID нужно согласовать адаптер с фактическим контрактом сервера и отдельно воспроизвести случаи дома, участка, помещения, архивного и виртуального объекта.

## 24. Проверка следующих улучшений

Следующие итерации должны проверять переносимость правил на другие организации и новые варианты адресов.

1. Отбирать новые ИНН по наличию паттернов, включая ранее не встречавшиеся формы помещений и территорий.
2. Выделять часть организаций для проверки после изменения правил. Адреса одного дома держать в одной группе.
3. Размечать небольшой набор спорных домов и помещений. Проверять правильность дома, сохранность помещения и основания географического выбора отдельно.
4. Повторять сравнение на пустой БД, прогретой БД и при перестановке организаций и пачек.
5. Сохранять ответы провайдеров вместе с версиями индекса и алгоритма, чтобы различать эффект изменения кода и обновления справочника.
6. Оценивать изменения по охвату организаций и паттернов, ошибочным успешным привязкам и стабильности `Address.id`.
7. Отдельно проверить штатные timeout и UUID-ветку на живых ответах провайдеров.
